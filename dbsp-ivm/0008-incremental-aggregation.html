DBSP 教学 · Lesson 0008 · 约 30–35 分钟

增量聚合：线性统计量与结果行构造

教程制作 · 李金懋（OceanBase）

本课用同一组 East 订单，逐层走完分组、SUM/COUNT 与结果行构造，并从单批推导得到对应的增量流电路。

依据：DBSP 论文 §7.2（Aggregation）、§7.3（Grouping）与 §7.4（GROUP BY-AGGREGATE）。

1. 问题：总和加了 10，为什么输出不是加一行 +10？

查询：

SELECT region, SUM(amount) AS total FROM orders GROUP BY region

注：本课假设 amount 不为 NULL（否则「组非空但 SUM 为 NULL」需额外维护非 NULL 计数），且每个批边界的输入快照都是合法 SQL bag——快照中每条记录权重 ≥ 0、删除不超过现有份数，故批边界的组内记录数不为负，count > 0 才能作为「组是否存在」的信号。此约束只管批边界快照；一批之内的变化流中，删除仍用负权重表示。

表结构为 orders(id, region, amount)，本课只跟踪 East 组：变化前组内有两笔订单 o1、o2，本批发生两笔变动：

订单本批操作对组内总和的影响
o3插入，金额 15+15
o1删除，金额 5−5

组内总和从 30 变为 40。很多人会想：总和多了 10，输出增量就是 +(East,10)。先把各层对象摆清楚，再看这为什么错。

状态对象本批开始前应用本批变化后
East 组基表记录 {(o1,East,5)↦1, (o2,East,25)↦1} {(o2,East,25)↦1, (o3,East,15)↦1}
组内记录数 count 2 2
组内总和 sum 5+25=30 25+15=40
SQL 结果关系 V {(East,30)↦1} {(East,40)↦1}

输出增量是新旧两个结果关系之差，按 Z-set 减法逐条记录计算：

ΔV = Vnew − Vold // 输出变化 = 新旧结果关系之差 = {(East,40)↦1} − {(East,30)↦1} // 代入上表两列 = {(East,40)↦+1, (East,30)↦−1} // Z-set 减法：缺席一侧的权重取负

直觉写法 {(East,10)↦1} 错在哪里？下游会把增量加到旧结果上：{(East,30)↦1} + {(East,10)↦1} 得到的是 (East,30) 与 (East,10) 两行，而不是真实新结果 {(East,40)↦1}。

两层对象不同：
  • 内部统计量 sum 是数字：30 → 40，变化量 +10。
  • SQL 结果关系 是表：必须 −(East,30) + (East,40)，撤回旧行、插入新行。

本课主线：按论文把查询拆开，看哪一层可以“直接加”，哪一层必须“新旧结果行之差”。

2. 先明确快照算子：三个不同层次

要推导一批变化如何传播，先明确完整快照查询究竟做了什么。论文不把 GROUP BY SUM 当成一个不可分的算子，而是拆成：

输入订单 Z-set → ① 按 region 分组 → ② 对每组计算 count 与 sum → ③ 按组是否存在，把 (region, sum) 构造成结果行

这三层处理的对象不同：第①层输出按键索引的子 Z-set，第②层输出内部标量，第③层输出 SQL 结果关系中的记录。继续用第 1 节变化前的 East 快照逐层计算。

2.1 第①层：按键分组

分组键函数 p 读取订单的 region。分组算子 Gp 把每条记录送到对应键的子 Z-set，并保留原权重：

Xold = {(o1,East,5)↦1, (o2,East,25)↦1} Gp(Xold)[East] = {(o1,East,5)↦1, (o2,East,25)↦1}

Gp(X) 是 indexed Z-set：每个键对应一个组内子 Z-set；两个 indexed Z-set 相加时，同一键下的子 Z-set 按记录权重相加。

2.2 第②层：对组内子 Z-set 计算两个标量

对组内子 Z-set s，定义：

aCOUNT(s) = Σx s(x) aSUM(s) = Σx amount(x) × s(x)

这里的 aCOUNT 统计组内记录数，对应 COUNT(*)。由于本课已假设 amount 不为 NULL，它也等于参与 SUM 的记录数；允许 NULL 时，两种计数必须区分。

对 East 桶：

aCOUNT = 1 + 1 = 2 aSUM = 5×1 + 25×1 = 30

这一层输出的是内部状态，不是 SQL 结果表。记为：

Sold[East] = (countold=2, sumold=30)

为什么 SUM 还要 count？如果某组所有 amount 碰巧加起来是 0，只看 sum=0 分不清“组里没有行”和“组里有行但总和为 0”。普通 GROUP BY 在组内没有行时，结果表里根本不出现该组；所以要用 count 判断组是否存在。

2.3 第③层：由内部状态构造结果关系

论文用 makeset 把一个值包装成只含该记录、权重为 1 的 Z-set：

makeset(v) = {v ↦ 1}

每组输出函数还要根据 count 判断该组是否存在：

out(g,count,sum) = ∅ 若 count = 0 makeset((g,sum)) 若 count > 0

因此旧 East 状态产生：

outold[East] = out(East,2,30) = makeset((East,30)) = {(East,30)↦1}
到这里仍是完整快照计算：订单 → 分组子 Z-set → (count,sum) → 结果行。接下来只改变这条流水线的输入，逐层计算每一层真正发生的变化。

3. 增量聚合流水线

变化前的三层结果已经算出。现在应用本批输入变化：

d = {(o3,East,15)↦1, (o1,East,5)↦−1}

目标仍是新状态与新结果行（sumnew、Vnew），但做法不是把新快照 Xold + d 重新过一遍三层。若某层保持加法，就有「新输入的层输出 = 旧输出（第 2 节已算）+ 本批变化的层输出」——这层只需处理 d，把贡献加到旧结果上；不能这样拆的层，才需要比较新旧。下面逐层验证哪层可以只处理 d。

3.1 分组层：变化按键进入对应子 Z-set

先验证分组层可以只处理 d。分组不修改记录和权重，只按 region 选键，因此保持加法：

Gp(Xold + d) = Gp(Xold) + Gp(d)

等式两侧都是 indexed Z-set，加法按键逐点进行。左侧是新快照的分组结果；右侧把它拆成第 2 节已有的 Gp(Xold) 与只依赖本批的 Gp(d)——所以本层只需计算后者。本批两条变化都属于 East：

Gp(d)[East] = {(o3,East,15)↦1, (o1,East,5)↦−1}

未出现在 d 中的分组不受影响，不需要重新读取。

3.2 标量层：直接累加 count 与 sum 的变化

COUNT 和 SUM 的定义都是加权和。对任意两个组内 Z-set A、B，整数加法的分配律给出：

aCOUNT(A+B) = aCOUNT(A) + aCOUNT(B) aSUM(A+B) = aSUM(A) + aSUM(B)

因此无需对新的 East 子 Z-set 重新求和，只计算本批变化的贡献：

Δcount = (+1) + (−1) = 0 Δsum = 15×(+1) + 5×(−1) = 10 countnew = 2 + 0 = 2 sumnew = 30 + 10 = 40 Snew[East] = (count=2, sum=40)

这一步得到的是内部标量变化 Δsum=10，尚未得到 SQL 结果关系的变化。

3.3 结果层：用新结果行减旧结果行

新旧 count 都大于 0，所以 East 组前后各有一条结果记录：

outold = makeset((East,30)) = {(East,30)↦1} outnew = makeset((East,40)) = {(East,40)↦1} ΔV = outnew − outold = −(East,30) + (East,40)

这里不能把 makeset 直接用于 Δsum=10：

makeset((East,10)) = {(East,10)↦1} makeset((East,40)) − makeset((East,30)) = {(East,40)↦1, (East,30)↦−1}

两者不是同一个 Z-set，所以 makeset 不保持加法，是非线性的。内部数字可以从 30 加 10 得到 40；结果关系却必须用完整新行替换完整旧行。

同一批变化沿三层传播后，结论自然出现：分组变化可直接路由，统计量变化可直接累加，结果行变化必须比较新旧状态。

4. 从单批推导归纳为增量算子

先给第 3 节的三个阶段命名，并约定类型记号：

记号含义
ℤ[Order]订单 Z-set：订单记录 → 整数权重。
ℤ[Order][Region]以 region 为键的 indexed Z-set：键 k 处存放该组的订单子 Z-set。
State「分组键 → (count,sum)」的有限映射，缺失键默认取 (0,0)。
Result = (Region,Total)结果记录的形状：分组键 + 组内总和。
Gp分组层：把订单 Z-set 按 region 拆到各键名下。
A标量层：每组算出 (count,sum) 标量对。
emit结果层：按 count 判断组是否存在，存在的组经 makeset 拼成结果行。
E(Sold, ΔS)新旧比较：由旧 State 与状态变化算出结果关系的变化（下文定义）。

四个算子的类型为（X → Y 表示「输入 X、输出 Y」）：

Gp : ℤ[Order] → ℤ[Order][Region] A : ℤ[Order][Region] → State emit : State → ℤ[Result] E : State × State → ℤ[Result]

E 的第二个 State 参数表示状态变化，可正可负。A、emit 与整条查询 Q 的定义为：

A(g)[k] = (aCOUNT(g[k]), aSUM(g[k])) emit(S) = Σk out(k, S[k].count, S[k].sum) Q = emit ∘ A ∘ Gp

A 的输出是“分组键 → (count,sum)”的有限映射，其加法按键逐点进行。由于 COUNT 与 SUM 都保持加法，A 也保持加法。emit 包含组存在性判断、结果值构造和 makeset，不是线性算子。

整条快照查询为 Q。高效实现必须产生的结果由朴素增量定义：

(↑Q)Δ = 𝒟 ∘ ↑Q ∘ ℐ

论证分三步：先证明分组状态可以只凭变化增量维护（4.1）；再用新旧状态定义输出变化算子 E（4.2）；最后证明两者组成的高效电路与朴素定义逐时刻相等（4.3）。

4.1 第一步：增量维护分组状态

令 d 是订单变化流。依次定义：

dk = ↑Gp(d) // 本批变化按键分组 ΔS = ↑A(dk) // 各组状态变化 (Δcount,Δsum) S = ℐ(ΔS) // 状态流：应用本批后的新状态 Sold = z⁻¹(S) // 旧状态：上一时刻的状态

对任意逻辑时刻 t：

  • dk[t] 是本批按键分组后的记录变化；
  • ΔS[t][k] 是组 k 的 (Δcount,Δsum)；
  • S[t][k] 是应用本批后的 (count,sum)（与第 3 节的 Snew 对应）；
  • Sold[t][k]=S[t−1][k] 是应用本批前的旧状态（与第 3 节的 Sold 对应）。

令 s=ℐ(d) 是完整输入的快照流。因为 Gp 与 A 都保持加法，它们与积分可交换，所以增量维护的状态等于对全量快照直接计算的状态：

S[t] = A(Gp(s[t])) // S=ℐ(↑A(↑Gp(d)))，保持加法 ⇒ 与 ℐ 交换

至此状态半边完成：分组状态只凭变化即可增量维护，且与全量计算的状态一致。剩下的是由状态构造输出变化。

4.2 第二步：用新旧状态构造输出变化

emit 不是线性算子，不能把 ΔS 直接变成输出变化；但有了 4.1 的旧状态 Sold 与状态变化 ΔS，就可以用新旧比较来构造。定义快照算子 E，它接收旧分组状态 Sold 与本批状态变化 ΔS：

E(Sold, ΔS) = emit(Sold + ΔS) − emit(Sold) = Σk ( out(k, (Sold + ΔS)[k].count, (Sold + ΔS)[k].sum) − out(k, Sold[k].count, Sold[k].sum) )

若 ΔS[k]=(0,0)，该组的新旧两项抵消。因此实现只需遍历 ΔS 中发生变化的键。第 3 节 East 的计算正是 E(Sold[t], ΔS[t]) 的一次展开。

相应的高效流电路是：

(↑Q)Δ(d) = (↑E)(Sold, ΔS) 其中： dk = ↑Gp(d) ΔS = ↑A(dk) Sold = z⁻¹(ℐ(ΔS))

4.3 第三步：证明与朴素形式相等

沿用 4.1 的 s=ℐ(d)，令 y=↑Q(s)。约定 s[−1]=0、S[−1]=0，因此 Q(0)=emit(0)=0。对任意逻辑时刻 t：

(𝒟 ∘ ↑Q ∘ ℐ)(d)[t] = 𝒟(y)[t] // s=ℐ(d)，y=↑Q(s) = y[t] − y[t−1] // 𝒟 的定义 = Q(s[t]) − Q(s[t−1]) // ↑Q 的定义 = emit(S[t]) − emit(Sold[t]) // Q=emit∘A∘Gp，4.1：S[t]=A(Gp(s[t])) = emit(Sold[t] + ΔS[t]) − emit(Sold[t]) // S[t]=Sold[t]+ΔS[t] = E(Sold[t], ΔS[t]) // E 的定义 = (↑E)(Sold, ΔS)[t]

所以高效电路与朴素增量定义同一个流算子。效率来自线性层直接处理变化，以及 E 只比较受影响组；不是改变输出语义。

4.4 合并后的实现顺序

对每个本批受影响的组 g：

1. 读取旧状态 (countold, sumold) 2. 用本批变化计算 Δcount、Δsum，得到新状态 3. 由新旧状态构造 outold、outnew （count=0 时该侧无输出行） 4. 发射 ΔV[g] = outnew − outold 5. 提交新状态

必须先读旧状态、再算输出、最后提交。若先覆盖状态，就丢失了要撤回的旧结果行 (g, sumold)。

朴素形式

𝒟 ∘ ↑Q ∘ ℐ：恢复完整输入，重跑整条分组聚合，再差分。定义“结果必须是什么”。

高效形式

(↑E)(z⁻¹(ℐ(ΔS)), ΔS)：线性层产生状态变化，只对受影响组执行完整的 outnew−outold。

5. 同一公式覆盖组出现与组消失

第 3 节是组前后都存在。若 count 穿越 0，仍然只需使用 outnew−outold，不需要增加新的增量规则：

旧 count新 count输出变化含义
0> 0+(g, sumnew)新组第一次出现，只需插入
> 00−(g, sumold)组内最后一行被删光，只需撤回
> 0> 0−(g,sumold)+(g,sumnew)组仍在；若 sum 相同则两项抵消

例如原先没有 West，本批插入 (w1,West,7)：

count: 0 → 1，sumnew=7 ΔV = +(West,7)

若再删除这唯一一行：

count: 1 → 0 ΔV = −(West,7)

这仍是完整结果构造函数 out 的新旧之差，不是 SUM 公式之外的新规则。

6. 边界：AVG 与 MIN/MAX

  • AVG：先线性地维护 (sum, count)，在结果值构造阶段计算 sum/count，再用 makeset 包装 (g,avg)。除法与结果行构造不线性，但标量状态仍可只更新变化的组。
  • MIN / MAX：删除当前极值时，一般不能只看本批变化。通用形式是 (↑aMIN)Δ = 𝒟 ∘ ↑aMIN ∘ ℐ，可能需要完整组内容；工作量可与当前关系大小成正比。有序多重集等加速是物理优化，不是该通用等式自动给出的复杂度。
边界：主结论针对合法 bag、聚合列不含 NULL 的 SUM/COUNT。amount 可为 NULL 时需另维护非 NULL 计数；MIN/MAX 的专用索引不是 DBSP 通用增量等式。

7. 小结

  1. 分组聚合依次处理分组子 Z-set、内部 (count,sum) 状态和 SQL 结果行，三者不能混为同一对象。
  2. 沿同一批变化推导可见：Gp、aSUM、aCOUNT 保持加法，可以直接处理变化。
  3. 完整结果构造层 emit/out 包含组存在性判断与 makeset，不保持加法；它必须比较新旧标量状态。
  4. 因此 SUM 从 30 到 40 时，内部变化是 +10，结果关系变化是 −(East,30)+(East,40)。
必须能脱稿写出： (↑Gp)Δ = ↑Gp (↑aSUM)Δ = ↑aSUM 内部：sumnew = sumold + Δsum 外部：ΔV[g] = outnew − outold = −(g,sumold) + (g,sumnew) // 当组仍存在且 sum 变化时 高效流电路： dk = ↑Gp(d) ΔS = ↑A(dk) Sold = z⁻¹(ℐ(ΔS)) (↑Q)Δ(d) = (↑E)(Sold, ΔS) E(Sold, ΔS) = emit(Sold + ΔS) − emit(Sold)
