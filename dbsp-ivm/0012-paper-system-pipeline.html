DBSP 教学 · Lesson 0012 · 约 25–30 分钟

从 SQL 编译到增量运行时：完整系统管线

教程制作 · 李金懋（OceanBase）

本课把 Z-set 电路、自动增量化、状态维护和运行时执行放进同一张系统图，并总结论文原型的实现边界。

依据：DBSP 论文关于线性、双线性、非线性算子以及递归电路的增量化定义与定理。

1. 把数学电路放回编译器和运行时

下面把增量公式放入编译器、运行时和状态存储的完整系统路径。概念层的整体路径：

SQL → 解析、类型检查与关系代数 → Z-set/DBSP 普通电路 → 增量化与优化 → 可执行数据流程序 → 运行时接收输入批次、维护状态、输出 delta
范围声明：这里描述 DBSP 论文原型和概念层系统结构，不声称等同于 2026 年 Feldera 仓库的当前目录、接口或部署架构。查看现行实现时应以对应版本的官方代码和文档为准。

2. 编译阶段一：SQL 先变成有类型的关系计划

SQL 文本包含名称解析、类型、NULL、bag/set 语义等细节，不能直接拿字符串做代数变换。论文系统路线中，SQL 前端借助关系查询编译基础设施完成解析和优化，再交给 DBSP 编译层。

输入： CREATE VIEW v AS SELECT region, SUM(amount) FROM orders WHERE amount >= 20 GROUP BY region; 关系计划（简化表示）： Aggregate[group=region, sum(amount)] Project[region, amount] Filter[amount>=20] Scan[orders]

这一阶段的责任是确认列、类型和 SQL 语义，并做合法的关系优化；它还没有决定每一批 delta 如何执行。

3. 编译阶段二：关系算子翻译成 Z-set 电路

关系/SQL 节点Z-set 电路节点增量性质
WHERE / selectionfilter线性，严格为 (↑O)Δ=↑O
projection / expressionmap线性
UNION ALLZ-set 加法线性
JOIN双线性 join三项 delta
DISTINCT阈值/计数算子需要 multiplicity 状态
GROUP BY分组聚合算子需要组状态和输出行替换

翻译结果是普通快照函数 Q 的电路表示。每条边都有记录类型，每个节点都有明确的 Z-set 语义。

4. 编译阶段三：统一增量化，而不是逐 SQL 模板手写触发器

编译器从统一定义开始：

完整论文记号：(↑Q)Δ = 𝒟 ∘ ↑Q ∘ ℐ Q 是快照查询 ↑Q 是 lifted 流算子 (↑Q)Δ 是流算子 ↑Q 的增量算子

再使用链式法则把增量化推入电路，按节点性质替换：

线性节点： (↑O)Δ = ↑O 双线性 join： ΔL⋈Rold + Lold⋈ΔR + ΔL⋈ΔR Distinct： 维护旧计数，比较新旧存在性 Aggregation： 更新组状态，撤回旧结果并插入新结果 Feedback： 增量化递归体，传播 frontier
关键工程价值不是“系统内置几条特殊 delta SQL”，而是普通电路先有统一语义，再由可组合规则系统地得到增量电路。

5. Algorithm 4.8：论文给出的五步机械流程

  1. 按论文 Table 1 把关系查询 Q 翻译为 Z-set 电路。
  2. 反复应用 distinct consolidation 等等价变换，直到不能继续。
  3. 把整条快照电路 lift 到流上，得到 ↑Q。
  4. 外包积分与微分，得到语义正确但可能低效的 (↑Q)Δ=𝒟∘↑Q∘ℐ。
  5. 利用 chain rule 及各类增量恒等式，递归把 Δ 推入内部节点并化简。
这五步把“正确性基线”和“性能优化”分开：第 4 步先保证结果正确，第 5 步再消去不必要的全量恢复与重算。

6. 编译阶段四：优化和生成可执行程序

逻辑正确的增量电路仍可能包含冗余状态或算子。编译阶段可继续做保持语义的优化，例如消除可证明冗余的 distinct、融合线性算子、选择 join 的索引和物理布局。

增量逻辑电路 → 电路优化 → 物理算子与状态布局 → 生成/构造 Rust 数据流程序 → 编译为运行时可执行代码

论文和早期系统资料常用“生成 Rust、使用 DBSP runtime”描述后端。这里应把它理解为一条论文系统路线，而不是承诺当前代码仍使用完全相同的模块名和生成边界。

7. 运行阶段：每一批数据实际发生什么？

顺序运行时动作对应概念
1输入适配层把 INSERT/DELETE/UPDATE 编码成 Z-set deltaZ-set 变化编码
2线性节点直接转换本批记录线性增量算子
3join 读取旧状态（物理实现可通过索引访问）并计算三项贡献双线性 join
4distinct、aggregation 读取旧状态并产生输出变化状态化非线性算子
5递归子图反复推进 frontier 直到稳定递归反馈与 frontier
6提交本批新状态，把输出 delta 交给下游批次状态提交
一个事务/批次的原子边界很重要：算 delta 时要明确使用 old 状态，计算完成后再让 new 状态成为下一批的 old 状态。

8. 编译器、运行时、状态存储各自负责什么？

SQL/DBSP 编译器

守住查询语义；构造并增量化电路；进行合法优化；决定需要哪些状态和索引。

执行运行时

调度算子、传递批次、执行并行计算、推进递归轮次，并产出变化流。

状态与索引

保存 join 两侧历史、distinct 计数、聚合组状态、递归已知集合等。

输入/输出适配

把外部变更转成 Z-set delta，把结果 delta 送往物化视图、消息系统或其他消费者。

DBSP 理论主要规定电路和增量化语义；事务一致性、恢复、资源管理和部署接口仍需要系统工程设计。

9. 正确性怎样分层验证？

  1. 算子级：对每个节点比较“增量执行后状态”与“在新快照上全量执行”。
  2. 电路级：累计 (↑Q)Δ 输出，比较 Q(ℐ(d))。
  3. SQL 级：使用包含 NULL、重复、删除、聚合和边界条件的查询测试。
  4. 系统级：验证批次提交、故障恢复和输出一致性不会破坏代数假设。
核心测试 oracle： ℐ((↑Q)Δ(d)) = ↑Q(ℐ(d))

左边累计增量查询的输出；右边在每个完整快照上运行原查询。两边相等就是最直接的端到端正确性标准。

10. 2023 论文原型明确报告了什么？

  • 以 Rust 实现 DBSP library 与 data-parallel multicore runtime，并提供电路构造 API。
  • 运行时包含通用 integration、differentiation、delay 与 nested operators；算子状态可在需要时 spill。
  • 论文原型提供 Kafka/CSV 输入输出适配。
  • SQL-to-DBSP 编译器建立在 Apache Calcite 上；论文报告通过约 700 万条 SQL Logic Tests。
  • 核心形式化另有约 5K 行 Lean 证明，用于验证关键代数性质。

以上各项为 PVLDB 2023 论文 §8 的报告；arXiv 预印本（2203.16684）的 §8 更短，仅报告 Rust 原型库，SQL 编译器与 Lean 形式化是 PVLDB 版新增的。PVLDB PDF：https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf。

版本声明：这些是 2023 PVLDB 论文对原型的报告，不代表 2026 年 Feldera 仓库目录、组件边界或测试数字保持不变。

11. 时间模型与系统边界

DBSP 基础模型中的外层时间是线性化事务的同步、全序逻辑时间，而不是 wall clock。递归通过 nested streams 增加内部迭代维度，但外层事务仍按顺序处理。

因此，乱序事件、多输入 watermark/progress、部分序时间 lattice 等问题不能仅凭这些公式自动解决；它们需要输入层排序、协调协议或更丰富的时间模型。DBSP 的简化换来的是更直接的统一增量化代数。

该边界同时对照 DBSP 论文与 Murat Demirbas 的 DBSP 阅读笔记；博客把它与 Differential Dataflow 的部分序时间/progress 机制进行了对比。

12. 与真实系统的对照

A. 论文 §9 的位置：与 DD / DBToaster 的关系

论文相关工作把 DBSP 放在两条已有线索之间。

Differential Dataflow (DD)。论文明确说 DBSP 的所有算子都基于 DD 的算子。DD 的计算模型更一般、更强：它允许流中过去的值被修订，时间戳可以是偏序。DBSP 刻意把外层时间限制为全序的线性时间，从而简化进度（progress）问题。非嵌套流上的 DBSP 可看作 Kahn network 的简化实例。

传统 IVM / DBToaster 一脉。传统增量视图维护沿「把 delta 沿代数表达式传播」的路线发展：

Q(R + ΔR) = Q(R) + ΔQ(R, ΔR)

该路线最终结晶于 Koch 等人的工作（论文引文 [22]）。论文的自评是：DBSP 的增量化更模块化、粒度更细——它处理的是更新流而非单次 delta，并且能覆盖递归与非单调查询。

B. 与 OceanBase 物化视图的对照

OceanBase 支持物化视图（MV）。刷新方式有 FAST（增量刷新）、COMPLETE（全量刷新）、FORCE；刷新时机有 ON COMMIT / ON DEMAND。FAST 刷新依赖基表的物化视图日志（mlog）记录变化行的 old/new。增量刷新规则按查询形态在内核中工程化实现；不支持的查询形态回退为全量刷新。

用本课程已建立的概念对照：

  1. 变化的统一建模。mlog 的 old/new 行对应 Z-set 的负/正权重。DBSP 把「数据」和「变化」统一为同一类对象，是整个框架的起点（第 0002 课）。
  2. 手工规则 vs 机械推导。OceanBase 按算子类别工程化增量规则；DBSP 由 Algorithm 4.8 对任意查询机械生成增量电路，并有正确性定理 ℐ((↑Q)Δ(d)) = ↑Q(ℐ(d))。
  3. 状态解释限制。distinct 需要旧权重 H（第 0007 课），join 需要两侧旧状态（第 0006 课）——增量算子的状态需求解释了为什么各数据库的 FAST 刷新都对查询形态有限制。
  4. 边界。递归与非单调查询的增量化超出传统物化视图的常见范围，是 DBSP 的额外覆盖。
范围声明：OceanBase MV 的具体算子支持矩阵与语法随版本变化，以官方文档为准；本节目的为概念对照，不是 OB 功能手册。

13. 核心概念总结

  1. 为什么变化和快照都用 Z-set 表示，以及负权重如何表达删除。
  2. ↑、z⁻¹、ℐ、𝒟 各自处理什么。
  3. (↑Q)Δ=𝒟∘↑Q∘ℐ 的语义和链式法则的效率意义。
  4. 线性、双线性 join、distinct、aggregation 的增量推导。
  5. 一条 SQL 如何翻译为 Z-set 电路，并逐层处理输入变化。
  6. 递归为什么是反馈不动点，以及 frontier 为什么能避免重复工作。
  7. 编译器与运行时如何把这些代数规则变成持续执行的系统。
核心理论与系统路径已经形成闭环。可用以下方式检验理解：选一条含 join、distinct、aggregation 的 SQL，在白板上手推两批插入/删除并用全量重算复核。
