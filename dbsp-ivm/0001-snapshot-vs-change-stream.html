DBSP 教学 · Lesson 0001 · 约 15 分钟

快照流 vs 变化流

教程制作 · 李金懋（OceanBase）

本课建立 DBSP 的时间模型：同一段数据库历史既可以表示为完整快照序列，也可以表示为逐批变化序列。两种表示通过累积与差分互相转换。

依据： DBSP 论文 §1–2 · arXiv:2203.16684

1. 论文要解决什么问题

问题

基表改了一行，物化视图却要整库重跑查询——太慢。 想要的是：喂进去「改了什么」（ΔDB），直接拿到「视图变了什么」（ΔV），计算尽量跟变化规模相关，而不是每次都重复扫描全库。 这叫 IVM（增量视图维护）。

单条 SUM 谁都会手写增量。难的是：join、聚合、distinct、递归……任意组合能不能自动得到正确的增量版？ 以前靠人逐条 SQL 写规则，覆盖不全、易错、不可组合。

DBSP 的回答

你写普通查询 Q。编译器按固定算法把 Q 改写成增量版 (↑Q)Δ——运行时以 ΔDB 为输入、产出 ΔV，目标是尽量避免每次都整库重跑。 同一套改写流程覆盖一大类 SQL / Datalog，不用逐条手写。

关键点

  1. 从基表的增量 ΔDB 推导出视图的增量 ΔV，而不是重跑完整视图查询。
  2. 视图增量可沿查询结构继续拆分：复杂视图拆成复合单元，再拆成基础算子。只要基础算子的增量规则能高效实现，编译器就能把它们组合成复杂视图的增量计算。
  3. DBSP 借鉴离散信号处理的描述方式，用一套数学框架表达这套增量计算；论文进一步推导了 filter、project、join、distinct、group by 等典型基础算子的增量规则。

把这 5 个表按时间排成序列，就是快照流——每个时刻数据库的完整样子。

3. 变化流：每个时刻改了什么

同一段历史，换成只记「这一步相对上一步多了/少了什么」：

t 变化 Δ
0∅
1+A:10, +B:20
2+C:30
3−B:20
4−A:10, +A:25

这条序列就是变化流。

快照与变化可以互转

变化 → 快照（累积）

快照[t] = Δ[0] + Δ[1] + … + Δ[t]

把历史变化全加起来，就是当前完整表。
例：t=3，(+A10 +B20) + (+C30) + (−B20) = {A10, C30}。

快照 → 变化（差分）

Δ[t] = 快照[t] − 快照[t−1]

相邻两个快照做差，就是这一步的变化。
例：t=3 比 t=2 少了 B → Δ = −B。

论文把累积叫积分 ℐ，把差分叫微分 𝒟——名字来自信号处理，先当 cumsum / diff 理解即可。

统一记号：Xt 是第 t 步完整快照，dt 是第 t 步变化；各自打包成流 s=(X0,X1,…)、Δ=(d0,d1,…)，故 s[t]=Xt、Δ[t]=dt。约定 X0=∅、d0=∅，t ≥ 1 时 Xt=Xt−1+dt。

4. 视图也有快照流和变化流

CREATE VIEW total AS SELECT SUM(amount) AS s FROM orders;

对每个数据库快照执行查询，得到视图快照流；再对相邻视图快照做差分，得到视图变化流。这里用 SUM 的数字结果直观展示两种流：

torders 快照视图 SUMΔ(视图)
0∅00
1A10, B2030+30
2A10, B20, C3060+30
3A10, C3040−20
4A25, C3055+15

IVM 要的就是：输入「表的变化」，直接输出「视图的变化」——不必每次整表扫一遍再 SUM。

5. 维护视图的两种基本方式

全量重算——每次事务后对整表重跑查询。1 亿行改 1 行，仍扫 1 亿行。

手写增量——SUM 的增量很容易写（旧值 + 插入 − 删除），但查询变成 join + distinct + 子查询时，逐条设计、验证和维护规则的成本会迅速上升。

6. 小结

  • 快照流 = 每个事务后的完整表
  • 变化流 = 每个事务改了什么
  • 累积变化 → 快照；相邻快照做差 → 变化
  • IVM = 以变化驱动变化（ΔDB → ΔV），尽量避免重复全量计算
