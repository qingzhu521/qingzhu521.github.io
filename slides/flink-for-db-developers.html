业务背景 · 持续窗口聚合

持续计算订单表的五分钟成交总额

orders 是持续写入的订单明细表，每行包含订单编号、事件时间 event_time 与金额 amount。业务要求每个 5 分钟窗口的成交总额（GMV）在分钟级延迟内可见。
SELECT TUMBLE_START(event_time, INTERVAL '5' MINUTE) AS w,
       SUM(amount) AS gmv
FROM orders
GROUP BY TUMBLE(event_time, INTERVAL '5' MINUTE);

1定时轮询

每分钟重新执行整条 SQL。查询频率越高，结果越及时，数据库负载也越高。

延迟与系统负载相互制约；数据量增加后，全量重算成本持续上升

2触发器 / 物化视图

在每次数据写入时同步维护聚合结果。

维护开销进入写入路径，高并发场景下可能降低写入吞吐量

3缩短批处理调度间隔

将每日批处理缩短到小时级或分钟级，形成微批处理。

调度间隔越短，启动与协调开销占比越高；执行方式仍是周期性批处理
这三种方案都以有明确终点的一次性查询为前提。持续输入带来的根本变化在于执行模型，而非单纯的性能不足。

一、无界输入与执行模型

经典火山模型如何执行查询

在经典抽象中，open() → next() × N → close()。向量化、编译执行和 morsel-driven 调度主要降低执行开销，基本前提仍是输入有界、查询具有明确终点。

持续无界输入使三个基本前提不再成立

对于持续无界输入，结束边界不再由 close() 自然提供，因此状态生命周期、计算窗口与事件时间进度都必须显式管理。

二、从拉取式执行到数据流执行

由拉取式调用转向数据驱动的运行时调度

pull 模型通过调用关系组织执行，数据流模型由运行时根据输入可用性调度算子。计算的生命周期由一次性查询转为持续运行的服务。
二、从拉取式执行到数据流执行
二、从拉取式执行到数据流执行

dataflow 由持续运行的算子节点组成

GMV 查询被部署为一张持续运行的计算图。算子持续消费各自输入，运行时负责调度、数据交换与反压。
单机算子树可以部署为分布式常驻计算图：每个节点从固定输入读取、维护自身状态，并将结果发送到下游。这是数据流执行模型的基本形式（Kahn Process Networks，1974）。

三、事件时间、watermark 与迟到数据

乱序数据使窗口完成时间难以判断

系统按到达顺序接收记录，窗口却按事件时间归属。若没有显式的进度机制，立即触发与无限等待都会产生明显代价。
等待全部数据会长期阻塞输出，立即计算又可能遗漏记录。乱序是无界数据处理中需要常态化处理的情况。
三、事件时间、watermark 与迟到数据
三、事件时间、watermark 与迟到数据

watermark：事件时间进度的估计

运行时持续生成 watermark，表示系统认为事件时间已经推进到某个时点。窗口可以据此触发，但迟到数据是否接收仍由窗口策略决定。
DB 对照：有界输入由文件结尾提供完整性依据；无界输入使用 watermark 估计事件时间进度。示例中的 2 分钟是配置的乱序容忍量：取值越大，触发延迟越高；取值越小，迟到记录越多。
watermark 是进度估计，不是拒收规则。它决定计算何时触发；allowedLateness、侧输出等策略决定迟到记录如何处理。
三、事件时间、watermark 与迟到数据
三、事件时间、watermark 与迟到数据

allowedLateness：窗口触发后继续保留状态

以 allowedLateness = 5 分钟 为例：watermark 首次越过窗口结束时间时先输出结果，窗口状态随后再保留 5 分钟，以接收迟到记录。
allowedLateness 控制首次触发后的额外状态保留期：保留期内可以订正结果，状态清理后则无法由该窗口算子继续订正。
三、事件时间、watermark 与迟到数据
三、事件时间、watermark 与迟到数据

窗口结果的订正会继续影响下游计算

当 W1 由 60 订正为 85 时，下游若已根据旧值计算全天累计 GMV，就需要根据 changelog 语义同步更新受影响的结果。
在前缀累计示例中，W1 的变化会影响其后的累计结果。订正要求上下游就 append、upsert 或 retract 等 changelog 语义达成一致；Paimon 主键表与 changelog producer 可以保存并继续传播这种变化。

四、状态的托管与持久化

状态保存会影响后续计算的中间信息

窗口累加器、join 缓冲区和 distinct 已处理的 key 都会影响后续记录的计算结果，因此需要作为状态持续保存。
DB 对照：批处理的中间数据通常随查询结束释放；流式作业的状态需要在长期运行期间持续存在。凡是会影响后续输入处理结果的信息，都属于状态。
状态管理经历了从系统内部结构、应用自行维护到用户声明、运行时托管的演进。只有纳入运行时管理，状态才能统一参与快照、恢复与扩缩容。

五、checkpoint 与故障恢复

checkpoint：为分布式计算图保存一致状态快照

长期运行的有状态算子可能发生故障。仅重放输入不足以恢复计算，还必须同时保存算子状态与可重放数据源的消费位点（offset）。
DB 对照：数据库通过 checkpoint 与日志位点恢复；Flink 将这一思想扩展到分布式计算图。barrier 在拓扑中传播，多输入算子可能短暂等待对齐，但通常无需停止整个作业。
checkpoint 不是性能优化，而是有状态流计算实现一致恢复的基础：无状态作业可以直接重放输入，有状态作业还必须恢复与输入进度一致的状态快照。
五、checkpoint 与故障恢复
五、checkpoint 与故障恢复

不同状态机制对应不同的恢复语义

示例条件：聚合算子处理完 o6、尚未接收 o7 时发生故障。此时 W2 的状态应为 (o4, o6) = ¥100；恢复后继续处理 o7，最终结果应为 ¥170。
三个示例都依赖重放，差别在于故障前持久化了哪些状态与进度信息。若 Flink 使用非事务、非幂等 sink，恢复后的内部状态可以正确，但外部仍可能收到重复输出。

六、端到端 exactly-once 与 Paimon

状态 exactly-once 不等于端到端 exactly-once

checkpoint 可以将内部状态恢复到一致切面；但非事务、非幂等 sink 已发布的输出无法随之回滚，因此还需要控制外部可见性。
端到端 exactly-once 需要可重放 source、checkpoint，以及事务或幂等 sink 协作。Paimon sink 通过 snapshot 提交与恢复协议维护外部可见性；在这些前提成立时，恢复结果与无故障执行一致。
六、端到端 exactly-once 与 Paimon
六、端到端 exactly-once 与 Paimon

Paimon 在写入、恢复与结果订正中的作用

Paimon 不仅接收持续写入，还以已提交 snapshot 控制外部可见性；主键表保存订正后的值，可配置的 changelog producer 生成变更记录并供下游流式读取。
配置说明：完整的 −U/+U changelog 并非自动产生。input 仅适用于完整 changelog 输入；lookup 与 full-compaction 按各自机制生成；none 不保证旧值完整。下游须按 changelog 语义流式读取。
恢复时，Flink 恢复 state 与 source offset；Paimon 依据事务标识幂等完成提交，reader 仅读取已提交 snapshot。订正时，主键表保存更新值，配置后的 changelog producer 将变化传递给下游。

总结 · 概念对应

无界输入改变了执行、进度与一致性机制

无界输入带来的变化流计算机制有界查询中的对应概念
① 缺少预设结束边界常驻 dataflow：节点持续运行、输入位置固定火山模型：open / next / close，结束后释放
② 执行由输入与运行时驱动记录沿边传播，运行时调度对应算子pull：调用方通过 next() 控制执行
③ 事件时间数据可能乱序watermark 表示进度；迟到策略控制订正文件结尾提供完整性依据
④ 中间结果需要跨记录保留托管状态：用户声明、运行时管理查询中间状态随查询结束释放
⑤ 故障后需恢复状态与进度checkpoint：一致快照 + source offset 重放checkpoint + WAL / 日志位点
⑥ 外部输出需去重或原子提交事务或幂等 sink；Paimon sink 是一种实现数据库事务提交
流计算针对输入无界这一条件，提供持续执行、事件时间进度、状态管理和一致性恢复机制。
总结 · 概念对应
核心结论
watermark 提供事件时间进度
checkpoint 保存一致状态与恢复位置
事务或幂等 sink 控制外部可见性
watermark 随输入传播，checkpoint 由运行时协调，提交协议与 sink 协作。三类机制在语义上相互正交，共同保证持续计算结果可以触发、恢复并可靠地对外发布。
